## ⚠️ SECURITY INCIDENT (OLD SERVER, ARCHIVED) — compromise discovered 2026-07-03
**Historical record from the previous server, kept for reference only — confirmed NOT applicable to the current (2026-07-20+) server, see migration note above.** Original text follows unedited.

**This VPS was found root-compromised with a userland rootkit + Monero miner. Discovered while diagnosing an admin article-save 500 error — the "bug" was a symptom of the rootkit corrupting file permissions.** Full IOCs below. Do NOT assume the box is clean until the user confirms remediation + reboot + credential rotation are done.

- **Rootkit: `/usr/bin/systemded.so`** (31KB ELF, dropped Jul 2 17:08, root-owned). Listed in `/etc/ld.so.preload` → `LD_PRELOAD`-injected into **every dynamically-linked binary including our Node app**. Hooks `open/openat/fopen/opendir/readdir/readdir64` to hide files/processes (`check_hide`, reads `/proc/net/tcp*`). **Hides its own `ld.so.preload` entry**: `cat /etc/ld.so.preload` returns empty, but a raw `openat` syscall (bypassing the libc hook) shows `/usr/bin/systemded.so`. `ldd /usr/bin/node | grep systemded` confirms the injection.
- **Miner: `/bin/javae`** (5.5MB static ELF = **XMRig 6.25.0**, mtime Jun 18 — may be backdated or breach may predate Jul 2). Strings: `randomx.xmrig.com:3333`, `api.xmrig.com`, `/tmp/log.pid`.
- **Persistence: `/etc/cron.d/javae_hourly`** (dropped Jul 2 17:08) → `0 * * * * root /usr/bin/setsid /bin/javae >/dev/null 2>&1` (relaunches miner hourly as root).
- **Suspicious listeners** (identify as root with `lsof -iTCP:<port>`): `0.0.0.0:8083`, `*:3004`, and a `:53` daemon bound to the **public** IP `155.133.27.124` (normal resolvers bind `127.0.0.53`). NOTE: `*:3099` is NOT malicious — it's a stray leftover `node server.js` test instance (uid assam1, from Jun 24), safe to `kill`.
- **The file-permission tell:** the rootkit's `open/openat` hook mangles the mode arg, so **every file our Node process writes lands as mode `1101`/`1100` instead of `0644`** → unreadable uploads → Sharp "unsupported image format" → admin-save 500. If new uploads/generated files show weird perms (`---x-----T`), the rootkit is back. Clean-state test: `node -e "require('fs').writeFileSync('/tmp/t','x');console.log((require('fs').statSync('/tmp/t').mode&0o777).toString(8))"` must print `644`, not `1101`.
- **Incidental fix during triage:** article id 23573 ("Nazira residents oppose... health centre") had its featured image corrupted to mode 1101 by the rootkit; re-compressed + regenerated variants + re-attached `featured_image` manually. That article is fine; the root cause (rootkit) is the real issue.
- **Remediation status: NOT done by Claude** (root compromise = user's call; destructive). User has root on another terminal. Given root-level compromise, **rebuild-from-image + restore-from-known-good-backup is the only real guarantee**; surgical removal (rm cron → truncate ld.so.preload → rm binaries → pkill → reboot → verify `ldd node` clean) is containment only. **Rotate ALL `.env` secrets** (DB password, SESSION_SECRET, CF_API_TOKEN, FACEBOOK_PAGE_ACCESS_TOKEN, SENDPULSE_*, VAPID_*, hCaptcha) from a clean machine — root read that file for 2+ days. Entry vector unconfirmed (check HestiaCP CVEs, auth.log around Jul 2 17:08 and back to mid-June, rogue SSH keys/crontabs, web shells in upload dirs). **RESOLVED (2026-07-18): confirmed port-3000 app is map.guwahati.com, and yes it shares this host** — it's the original Node app built on this box (predates assamtimes.org), running under a separate Hestia/Linux user (`map`, home `/home/map/`, files not readable from the `assam1` account). This same investigation also surfaced that the box is a shared multi-tenant HestiaCP server with many unrelated customer accounts (`/home/rgvn`, `/home/kirtana`, `/home/apcc`, etc., all permission-denied from `assam1` as expected) plus a 3rd related site, `assam.org`, under yet another separate user (`assam`, home `/home/assam/`) — and a 4th, unnoticed-until-now domain, `myfamily.assam.org`, actually living under our OWN `assam1` account alongside assamtimes.org. Treat `assam.org`'s and `map.guwahati.com`'s files as equally off-limits as port 3000 always was.

## PDF Rendering
Reference for how `GET /article/:slug/pdf` actually works end-to-end — written up 2026-10-15/16 after a 28-day log investigation (~1,090 Puppeteer navigation timeouts, ~150 leaked `/tmp` Chrome profile dirs) and the two-phase fix that followed. The original feature description is still in Completed Features above (why Puppeteer + a shared singleton browser + `127.0.0.1` self-request instead of the public URL); this section is specifically about the concurrency/lifecycle machinery added on top of that.

**Files**: `src/utils/pdfBrowser.js` (browser lifecycle), `src/utils/pdfRenderQueue.js` (concurrency/dedup), `src/controllers/pdfController.js` (request handling), `public/robots.txt` + `rel="nofollow"` on both PDF links in `views/public/article.ejs` (keeps crawlers from walking every article's PDF link, the traffic pattern that caused the original overload).

**Queue (`pdfRenderQueue.js`)**: a plain in-process semaphore, not a library — max 2 concurrent renders, up to 10 more requests may wait, and a waiter times out after 20s if no slot frees up. Beyond 10 waiting, or past the 20s wait, the request never hangs — it rejects immediately (`QueueFullError`/`QueueTimeoutError`). Single-flight per article slug sits in front of the semaphore: concurrent requests for the *same* slug share one in-flight render and consume only one concurrency/queue slot between them, not one each — the common case for bot traffic (many simultaneous hits on one popular article's PDF link).

**503, not 500, for anything retryable**: `downloadPdf` maps `QueueFullError`, `QueueTimeoutError`, a `JobTimeoutError` (see hard ceilings below), Puppeteer's own `PuppeteerError` hierarchy, and a locally-defined `BrowserDisconnectedError` all to `503` + `Retry-After: 30`. The last one exists because Puppeteer does **not** consistently wrap disconnect-related failures in `PuppeteerError` — confirmed directly via a deliberate `kill -9` mid-render, which actually threw a plain `Error: Navigating frame was detached` (cause: `Error: LifecycleWatcher disposed`). Rather than trying to enumerate every message Puppeteer might ever throw, `renderPdf()` checks `browser.isConnected()` in its catch and re-throws as `BrowserDisconnectedError` if the browser itself is the reason — any other error still falls through to a generic `500`.

**Browser lifecycle (`pdfBrowser.js`)**:
- One shared browser, lazily launched on first request (fresh launch ~7.5s vs ~150ms to open a new page/tab on an existing instance). `getBrowser()`'s launch is itself single-flight (`startLaunch()`) — concurrent callers that both observe a disconnected browser do **not** each independently call `puppeteer.launch()`. This was a real, directly-reproduced bug: one deliberate kill produced 2 simultaneous browser processes + 3 leaked profile dirs before the fix, because the old check-then-launch wasn't atomic under concurrency.
- On disconnect, the dead browser is closed (with a timeout + SIGKILL fallback if `close()` itself hangs) **before** a relaunch is attempted — not after, and not skipped.
- Per-worker profile directory: `tmp/chrome-profiles/worker-<pid>` (app-owned, gitignored via `tmp/`), keyed by this Node process's own PID, not a random string. Fixed and reused across every relaunch of that worker — there's no new directory to leak on a crash+relaunch within the same worker, by construction. PM2 here runs `cluster_mode` with `instances: 1` (confirmed via `pm2 describe assamtimes` / `pm2 jlist`), so there's only ever one such directory in practice, but the PID-based naming means a future bump to `instances` can't have two workers collide on the same profile.
- Startup purge (`purgeStaleProfileDirs()`, runs once when the module loads): removes a leftover directory from this app's own `tmp/chrome-profiles/` **only if** its `SingletonLock` points at a PID that is not actually running — never by age. Verified directly: a confirmed-dead worker's directory was purged on the next startup, a confirmed-alive one was left alone. This matters because age-only deletion could have killed a slow-starting browser's directory, or (if `instances` is ever raised) another worker's still-live profile.
- Hard ceilings so nothing can hang the request indefinitely: a 35s per-job timeout around `page.goto()` + `page.pdf()` together (`page.pdf()` has **no** timeout option of its own in Puppeteer, unlike `goto` — this is the actual backstop for that gap, not redundant with goto's own 30s timeout), and a separate 5s timeout on `page.close()` in the `finally` block. If `page.close()` hangs, the whole browser process gets SIGKILLed (a page that won't close is treated as a sign the browser itself is wedged, not just that one page).
- Recycling: closes and lazily relaunches the browser after ~200 successful renders, or once tracked RSS crosses 3GB — **only when the render queue reports itself idle** (checked in `pdfRenderQueue.js`, called *after* `releaseSlot()`, not before, so the idle check reflects true post-release state rather than counting the just-finished render as still active). The 3GB figure is not a guess: an initial 1.5GB was picked blind and immediately caused recycle-almost-every-render thrashing once measured against this Chromium build's real baseline (~750-800MB completely idle, confirmed via direct `/proc` inspection) — direct measurement during testing showed sustained, non-crashing operation up to ~2.0-2.3GB under real concurrent load, so 3GB sits above that observed-healthy range instead of below it. A second calibration bug compounded the first: the module-level RSS tracking variable wasn't reset on a fresh launch, so a brand-new browser was being judged against the *previous* instance's stale, already-high RSS reading until its own 2s sampler had a chance to fire once — fixed by resetting it at the start of `launchBrowser()`.

**Findings that shaped the above, not just implementation notes**:
- **`page.close()` does not reliably reap the underlying renderer OS process on this Chromium build.** Confirmed directly, not assumed: a single isolated request (no concurrency, no other traffic) left 2 new, non-zombie renderer processes alive 20+ seconds after the request completed and `page.close()` had resolved, each holding real RSS (tens to hundreds of MB). This is why total browser RSS climbs with *cumulative* request volume rather than *concurrent* request count, and why capping concurrency at 2 (which is necessary and correct on its own) does not by itself prevent the browser from eventually needing to be recycled. Tried `--disable-features=BackForwardCache` directly as a candidate fix (a known Chromium flag for exactly this class of "renderer kept alive after navigation" behavior) — measured no meaningful difference in a controlled before/after comparison, so it was not added. Not chased further into Chromium's internal process-reuse heuristics beyond that; the periodic recycling above is the mitigation, not a fix for the underlying non-reaping itself.
- **A failed browser launch used to be cached permanently.** `getBrowser()`'s shared `browserLaunchPromise` previously had no cleanup path for a *rejected* launch — once `puppeteer.launch()` failed once (observed live: `Failed to launch the browser process: Code: null`, likely from a kill landing on a browser still mid-startup), every subsequent PDF request replayed the exact same rejection forever, with no self-healing retry, until the whole Node process was restarted. Fixed by attaching a side-effect-only `.catch()` to the launch promise at the point it's created (`startLaunch()`), which clears the shared reference on failure so the very next call gets a genuinely fresh attempt. Confirmed via an isolated test with a mocked one-time-failing launch (not live-server-risked): call 1 rejects as expected, call 2 retries cleanly and succeeds (`launchCallCount: 2`).

**Verified live, end to end, including the hardest case**: a deliberate `kill -9` landed mid-render (confirmed via `openPages=2` in the disconnect log, i.e. two renders genuinely in flight) produced a clean `503` with `Retry-After: 30` — not a hang, not a 500 — with zero change in leaked-directory count, exactly one relaunch, and the very next request succeeding normally (the queue keeps draining past a crash, it doesn't get stuck).

**Operational notes**:
- A root-owned hourly cron (`/etc/cron.d/clean-puppeteer-tmp` → `/usr/local/sbin/clean-puppeteer-tmp.sh`) deletes stale directories matching the *old*, pre-fix `/tmp/puppeteer_dev_chrome_profile-*` pattern (Puppeteer's own default, un-owned location) — **leave this alone**, it's root's, not ours, and it's not what cleans up after the current code at all. The app's own profile directory (`tmp/chrome-profiles/worker-<pid>`, app-owned, see above) is handled entirely by `pdfBrowser.js`'s own startup purge — the root cron has no reason to ever touch it and doesn't know it exists.
